
# Problem Statement

## DQE — Universal Dataset Query Engine

## 1. Introduction

Working with structured datasets often requires users to understand database concepts, write SQL queries, and use data-analysis tools. This creates a barrier for users who want to retrieve information from datasets but do not have sufficient technical knowledge.

The **Universal Dataset Query Engine (DQE)** aims to simplify this process by allowing users to ask questions about structured data using natural language.

The system accepts supported dataset formats, identifies their structure, converts natural-language questions into SQL queries, validates and optimizes those queries, and executes them in a controlled environment.

The objective is to make structured-data querying more accessible while maintaining query safety, execution reliability, and transparency.

## 2. Problem Definition

Users commonly face the following problems when working with structured datasets:

- They need SQL knowledge to retrieve specific information.
- Different file formats require different tools or processing workflows.
- Understanding unfamiliar schemas and column relationships takes time.
- Manually writing complex queries increases the possibility of syntax and logical errors.
- Unvalidated queries can create security and resource-consumption risks.
- Users may not understand how a query was generated or optimized.
- Query results are often presented without sufficient explanation or visualization.

DQE addresses these problems through a unified natural-language interface and a controlled query-processing pipeline.

## 3. Existing Challenges

### 3.1 Technical Knowledge Barrier

Users without SQL knowledge may struggle to perform filtering, aggregation, sorting, grouping, and other data operations.

### 3.2 Dataset Format Fragmentation

Data can be stored in different formats, including:

- CSV
- JSON
- Excel
- Parquet
- SQLite

Each format may require a different ingestion or processing method.

### 3.3 Schema Understanding

Users may not know:

- Available tables
- Column names
- Data types
- Relationships between columns
- Which fields are suitable for filtering or aggregation

### 3.4 Query Generation Errors

Natural-language questions can be ambiguous or incomplete. Automatically generated SQL may contain:

- Invalid column references
- Incorrect table references
- Syntax errors
- Unsupported operations
- Incorrect interpretations of user intent

### 3.5 Query Security

Executing arbitrary generated SQL can introduce risks such as:

- Data modification
- Unauthorized database operations
- Expensive queries
- Excessive result generation
- Resource exhaustion

### 3.6 Lack of Query Transparency

Users need to understand the SQL generated by the system, the optimizations applied, and the execution plan where available.

## 4. Proposed Solution

DQE provides a unified query engine with the following workflow:

1. Accept a supported dataset.
2. Ingest and normalize the dataset.
3. Infer its schema and metadata.
4. Store the data in a queryable SQLite database.
5. Accept a natural-language question.
6. Generate SQL using an LLM or template-based fallback.
7. Parse and validate the generated SQL.
8. Apply supported rule-based optimizations.
9. Execute the query using read-only database access.
10. Return the results with SQL, visualizations, and execution information.

## 5. Project Objectives

The primary objectives are:

- Support multiple structured dataset formats.
- Reduce the need for users to write SQL manually.
- Generate SQL from natural-language questions.
- Provide a fallback when an LLM provider is unavailable.
- Validate generated queries before execution.
- Restrict execution to permitted read-only operations.
- Apply rule-based query optimizations.
- Present results in understandable formats.
- Explain generated SQL and optimization decisions.
- Provide a CLI and web-based interface.

## 6. Functional Requirements

| ID    | Requirement            | Description                                     |
| ----- | ---------------------- | ----------------------------------------------- |
| FR-01 | Dataset Upload         | Accept supported dataset formats                |
| FR-02 | Data Ingestion         | Read and normalize uploaded data                |
| FR-03 | Schema Inference       | Identify tables, columns, and data types        |
| FR-04 | Natural Language Input | Accept questions in ordinary language           |
| FR-05 | SQL Generation         | Generate SQL using an LLM or fallback templates |
| FR-06 | SQL Validation         | Parse and validate generated SQL                |
| FR-07 | Query Optimization     | Apply supported optimization rules              |
| FR-08 | Query Execution        | Execute validated SQL against SQLite            |
| FR-09 | Result Presentation    | Display tabular results                         |
| FR-10 | Visualization          | Present suitable charts                         |
| FR-11 | Query Explanation      | Show SQL and optimization information           |
| FR-12 | CLI Support            | Provide command-line interaction                |
| FR-13 | Web Interface          | Provide a Streamlit interface                   |

## 7. Non-Functional Requirements

### Performance

- Keep ingestion and query execution efficient.
- Avoid unnecessary processing.
- Measure query latency across different dataset sizes.

### Security

- Use read-only database access for query execution.
- Reject unsupported or unsafe SQL operations.
- Apply execution time limits.
- Restrict the maximum number of returned rows.

### Reliability

- Handle invalid datasets and malformed queries.
- Provide meaningful error messages.
- Support fallback SQL generation when configured LLM services are unavailable.

### Usability

- Keep the natural-language interaction simple.
- Display results clearly.
- Make generated SQL and optimization decisions inspectable.

### Maintainability

- Separate ingestion, query generation, validation, execution, and presentation modules.
- Keep interfaces between modules well-defined.
- Support independent testing of core components.

## 8. System Constraints and Safety Limits

The proposed system uses the following operating constraints:

| Constraint              |       Limit |
| ----------------------- | ----------: |
| Maximum input size      |        1 GB |
| Maximum columns         |          20 |
| Query execution timeout |   5 seconds |
| Maximum returned rows   |      10,000 |
| Permitted query class   | SELECT-only |

These limits should be enforced by the implementation rather than treated only as documentation.

## 9. Success Criteria

The project defines the following target success criteria:

| ID   | Success Criterion                               |       Target |
| ---- | ----------------------------------------------- | -----------: |
| SC-1 | Correctness on a 50-question golden set         |       ≥ 85% |
| SC-2 | Unsafe-query rejection in a 100-case fuzz test  |         100% |
| SC-3 | Query latency improvement on 1-million-row data |       ≥ 30% |
| SC-4 | New-user onboarding time                        | < 60 seconds |

These are project targets. Actual results must be reported separately using reproducible test evidence.

## 10. Expected Outcome

DQE is intended to provide a unified interface for querying structured datasets without requiring users to write SQL manually.

The expected system should:

- Simplify dataset exploration.
- Reduce manual query-writing effort.
- Improve query safety through validation.
- Make query optimization understandable.
- Present query results in a user-friendly format.
- Support both command-line and web-based interaction.

## 11. Conclusion

The Universal Dataset Query Engine addresses the gap between natural-language questions and structured-data querying.

By combining dataset ingestion, schema inference, natural-language-to-SQL generation, query validation, optimization, controlled execution, and result visualization, DQE aims to make data querying more accessible, transparent, and reliable.
